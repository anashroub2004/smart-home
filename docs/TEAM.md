## 2. الملفات المشتركة — لا تُعدَّل إلا بالاتفاق

هذه الملفات هي "اللغة المشتركة" بين الأجزاء. تعديلها بدون اتفاق يكسر عمل الآخرين:

| الملف | ماذا يحدد | من يتأثر |
|---|---|---|
| `docs/contract.md` | شكل كل بيانات Firebase وكل رسائل MQTT | الجميع |
| `docs/seed.json` | الغرف والأجهزة والعتبات الأساسية (`schema`) | الجميع |
| `web/lib/contract.ts` | نفس العقد بلغة الويب | A |
| `pi/firebase_writer.py` | كيف يكتب الـ Pi في Firebase | B، C |
| `database.rules.json` | من يقرأ ويكتب ماذا | A، B |
| `docs/PROJECT_CONTEXT.md` · `CLAUDE.md` | القرارات وحالة المشروع | الجميع |

**طريقة تعديل ملف مشترك:**
1. اكتب في القروب: "أحتاج إضافة الحقل X في Y لأن..." وانتظر موافقة المنسّق.
2. التعديل يتم في **commit واحد** يغيّر `contract.md` + `contract.ts` + `firebase_writer.py` معاً (+ رفع `schema` إن تغيّر الشكل).
3. بعد الدمج: الكل ينفّذ `git pull`.

## 3. كيف تتواصل الأجزاء (الحدود بينها)

```
 D: ESP32  ──MQTT──►  B: Raspberry Pi  ──firebase_writer──►  Firebase  ◄──  A: الويب
                          │   ▲
                SQLite (readings)  │  قرارات AI (ai_schedule / suggestions)
                          ▼   │
                     C: الذكاء الاصطناعي
```

| بين | عبر | المرجع |
|---|---|---|
| D ↔ B | MQTT topics (`home/<room>/<device>/set` …) | `docs/contract.md` ← قسم MQTT |
| B ↔ A | مسارات Firebase (`/commands`، `/home_state` …) | `docs/contract.md` |
| B → C | جدول SQLite `readings(ts, key, value)` بمفاتيح `<room>/temp|lux|occ` و `device/<id>` | `ai/README_AR.md` |
| C → B/Firebase | `firebase_writer.write_ai_schedule / push_suggestion / write_ai_insights` | `pi/firebase_writer.py` |

**طالما كل شخص يلتزم بالعقد، يستطيع العمل وحده بدون انتظار الآخرين** — كل جزء له محاكٍ للجزء الذي قبله:
- A يعمل مع `sim_house.py` بدل الـ Pi.
- B يعمل مع `fake_nodes.py` بدل الـ ESP32 (يكتبه B).
- C يعمل مع `smart_home_ai.py demo` بدل بيانات حقيقية.
- D يختبر بـ MQTT Explorer أو `mosquitto_pub` بدل الـ Pi.

## 4. طريقة العمل على Git (لا أحد يكتب فوق عمل غيره)

### كل يوم قبل البدء
```powershell
git checkout main
git pull
git checkout -b <الجزء>/<وصف-قصير>      # مثال: web/edit-room  أو  pi/mqtt-ingest  أو  ai/dispatch
```

### أثناء العمل وبعده
```powershell
git add .
git commit -m "وصف ما فعلته بالإنجليزية"
git push -u origin <اسم-الفرع>
```
ثم على GitHub ← **Compare & pull request** ← **Create pull request**.
شخص آخر يراجع ويضغط **Merge** (أو المنسّق). بعد الدمج الكل ينفّذ:
```powershell
git checkout main
git pull
```

### قواعد
- **لا أحد يعمل مباشرة على `main`.** كل عمل في فرع، ويدخل `main` عبر Pull Request.
- اسم الفرع يبدأ باسم الجزء: `web/` · `pi/` · `ai/` · `fw/` · `contract/`.
- Pull Request صغير وكثير أفضل من واحد كبير بعد أسبوع.
- علامة ❌ في **Actions** على الـ PR = لا يُدمج حتى تُصلح.
- ظهرت `CONFLICT`؟ لا تحذف شيئاً — أرسل الرسالة لـ Claude أو للمنسّق.

### Firebase الحقيقي (`ai-home-aef50`) — شخص واحد لكل عملية
| العملية | من ينفّذها فقط | متى |
|---|---|---|
| `firebase deploy --only hosting --project prod` | A | بعد دمج تغييرات الويب في `main` |
| `python pi/sim_house.py --cloud ... --reset` | B | فقط عند تغيّر `schema` — **يُعلن في القروب أولاً** (يمسح البيانات) |
| `firebase deploy --only database --project prod` | المنسّق | عند تغيّر `database.rules.json` |

مفتاح الخدمة السري (`ai-home-key.json`) لا يُرسل لأحد — كل من يحتاجه يولّد مفتاحه من Firebase console.
للتطوير اليومي الكل يستخدم **المحاكيات المحلية** — لا أحد يحتاج القاعدة الحقيقية ليعمل.

## 6. ملف تحديث بعد كل جلسة عمل (إلزامي)

حتى تبقى كل المحادثات على نفس النهج — **لا ترى أي محادثة ما يحدث في غيرها**:

1. في نهاية كل جلسة، اطلب من Claude: **"اكتب ملف التحديث لهذه الجلسة"**.
2. يُحفظ في `docs/updates/YYYY-MM-DD_NN_<وصف>.md` حسب `docs/updates/TEMPLATE.md`، ويُرفع مع التعديلات.
3. **أرسل الملف لباقي الزملاء**، وكل زميل يرفقه في محادثته مع: "هذا تحديث من زميل، التزم به".
4. إذا كان التحديث يغيّر قراراً أو ملفاً مشتركاً، يُنسخ القرار أيضاً إلى `docs/PROJECT_CONTEXT.md`.

عند فتح محادثة جديدة: أرفق `PROJECT_CONTEXT.md` + `TEAM.md` + آخر ملفات في `docs/updates/` التي لم تقرأها.
